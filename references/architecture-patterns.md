# 架构图选择参考

仅在准备绘图时读取本文件。目标是选择最小适用架构，不是把所有层和 Agent 机制都塞进图中。

## 一、先选择系统形态

### 普通数字产品或服务

按需从下列层中选择：

1. **用户与入口**：Web、App、聊天、API、文件或设备。
2. **产品与业务**：账户、工作区、请求路由、核心业务规则、人工操作台。
3. **能力与编排**：确定性流程、智能能力、任务编排和结果校验。
4. **集成**：内部服务、第三方 API、通知渠道、支付或企业系统。
5. **数据与知识**：业务数据、文件、知识库、缓存、审计记录。
6. **运行与治理**：部署、队列、调度、监控、安全和权限。

没有实际职责的层可以省略或合并。

### AI 或 Agent 产品

当模型需要根据上下文自主选择动作时，按需使用：

1. **交互层**：谁在用、从哪里输入、同步还是异步。
2. **产品层**：会话、账户、请求路由和领域业务逻辑。
3. **Agent 编排层**：循环、工具分发、权限、任务、记忆或目标判断。
4. **模型层**：主模型、必要的辅助模型、路由与降级。
5. **能力集成层**：领域工具、知识检索、MCP 或第三方服务。
6. **数据层**：会话、任务、记忆、业务数据、日志与轨迹。
7. **基础设施层**：服务、沙箱、队列、调度、监控与密钥管理。

安全和可观测性通常是横切关注点，不必为了凑层数单独画成完整层。

### 固定工作流

如果步骤、顺序和分支都由业务规则预先确定，使用确定性工作流作为主干；只把确需理解、分类、生成或判断的步骤交给智能模块。不要把整个固定流水线包装成一个自主 Agent。

## 二、判断是否需要 Agent

满足以下一种或多种情况时，才考虑 Agent 或智能编排：

- 输入开放，无法用有限规则完整枚举。
- 需要根据上下文动态选择工具或下一步。
- 结果需要综合多种非结构化信息。
- 任务执行中必须观察结果并调整行动。

如果输入输出稳定、规则明确、步骤固定，优先画成普通服务或工作流。

## 三、按需求选择运行支撑组件

| 想法中的特征 | 架构图中可能需要的组件 | 选择提醒 |
| --- | --- | --- |
| 调用外部系统、API 或数据源 | 工具/集成层 | 标出输入、输出和副作用 |
| 存在删除、发送、付款等敏感动作 | 权限与审批 | 默认在动作前审批并记录审计 |
| 需要拦截、埋点或追踪调用 | 调用钩子 / 可观测性 | 画成横切能力或事件链路 |
| 多步骤且用户需要看到进度 | 计划或任务状态 | 区分临时计划与持久任务 |
| 领域资料很多 | 知识检索或按需技能 | 不要把所有知识塞进提示词 |
| 需要跨会话保存偏好或决策 | 记忆 | 标清写入、召回和用户控制 |
| 长任务或大量工具输出 | 上下文管理 | 只在长期运行确有需要时加入 |
| 慢操作不能阻塞交互 | 后台任务与通知 | 标出提交、执行、完成通知 |
| 到点自动运行 | 调度器 | 标出时区、幂等与失败处理 |
| 固定的多步骤编排 | 工作流运行时 | 让脚本拥有流程，模型处理单步判断 |
| 多个独立任务确实可并行 | 子任务或团队 | 标出任务隔离、汇总与资源边界 |
| “完成”难以由单次回答判断 | 结果校验或目标判断器 | 定义可观察的完成条件和退出路径 |

每加入一个组件，都要能回答：没有它，核心闭环会具体在哪里失败？如果答不上来，就删除。

## 四、图形表达规则

- 主链路从用户输入开始，以用户收到结果或外部状态改变结束。
- 外部参与者和第三方服务放在产品边界之外。
- 数据存储使用数据库形状 `[(名称)]`；普通能力使用矩形；人工确认使用清晰的“人工审批”节点。
- 实线箭头表示调用或数据流；如需表示异步事件，可在线上标注“事件/通知”，无需创造复杂图例。
- 一个节点只表达一个主要职责。若节点名称出现三个以上并列职责，考虑拆分。
- 优先显示模块责任和数据流，不在架构图中决定类名、函数名、文件路径或具体云产品。

## 五、最小质量检查

交付前确认：

- 图中能看出谁触发系统、系统交付什么。
- 每个主要节点都有明确职责，不把页面、功能名自动当成 Agent。
- 主数据流从输入到输出连续，没有无来源的数据或无接收方的结果。
- 外部系统、数据存储和产品边界清晰。
- 未知实现没有被写成事实。
- Mermaid 只有一张且结构不过度拥挤。
